# Каталог туристичних маршрутів вихідного дня

Лабораторна робота 1: «Від перевірки ідеї в notebook до перевіреного AI-сервісу».

Невеликий HTTP-сервіс каталогу туристичних маршрутів вихідного дня з трьома
функціями: ручне створення запису, перегляд списку, створення запису з
короткого тексту за допомогою LLM.

Ключова ідея: **модель пропонує, програма вирішує**. Модель не має прямого
доступу до сховища — вона повертає пропозицію, яку програма перевіряє власними
правилами і лише потім записує.

## API

| Метод і шлях | Що робить | Залежить від моделі |
|---|---|---|
| `POST /routes` | створює запис із полів, введених вручну | ні |
| `GET /routes` | повертає список записів | ні |
| `POST /routes/from-text` | приймає текст, отримує пропозицію, перевіряє і — лише тоді — створює запис | так |

### Формат запису

```json
{
  "name": "Соколиця",
  "distance_km": 12.5,
  "difficulty": "medium",
  "duration_hours": 4.0
}
```

| Поле | Тип | Допустиме |
|---|---|---|
| `name` | рядок | 3–80 символів |
| `distance_km` | число | 0.5–100.0 |
| `difficulty` | перелік | `easy` \| `medium` \| `hard` |
| `duration_hours` | число | 0.5–24.0 |

Усі чотири поля обов'язкові. Поля `id` і `created_at` додає сервіс; передавати
їх у запиті не можна (`422`).

### Відповіді

Успішне створення — `201` і створений запис:

```json
{
  "id": 1,
  "name": "Соколиця",
  "distance_km": 12.5,
  "difficulty": "medium",
  "duration_hours": 4.0,
  "created_at": "2026-10-20T09:15:00+00:00"
}
```

Список — `200`:

```json
{"items": [ ... ], "count": 1}
```

Порядок записів — за зростанням `id` (визначено специфікацією).

Помилка — завжди одна форма:

```json
{
  "status": "rejected",
  "reason": "invalid_semantics: distance_km не знайдено в тексті",
  "detail": "Пропозицію моделі відхилено"
}
```

| `status` | HTTP | Коли | Додаткові поля |
|---|---|---|---|
| `needs_clarification` | 422 | у тексті бракує даних | `missing`, `questions` |
| `rejected` | 422 | пропозиція порушує правила | — |
| `model_unavailable` | 503 | модель недоступна | — |

**HTTP-код і змістовий статус — різні перевірки.** `201` доводить лише те, що
запис створено, а не те, що його поля правильні. Клієнт перевіряє і код, і
`status`, і стан сховища.

## Налаштування

| Змінна | Типово | Призначення |
|---|---|---|
| `ROUTE_LLM_PROVIDER` | `openrouter` | `openai` або `openrouter` |
| `ROUTE_LLM_MODEL` | `minimax/minimax-m3.1-flash:free` | ідентифікатор моделі |
| `OPENROUTER_API_KEY` | — | ключ провайдера |
| `ROUTE_LLM_TIMEOUT` | `20` | таймаут одного виклику, секунди |
| `ROUTE_LLM_MAX_ATTEMPTS` | `2` | максимум спроб |
| `ROUTE_LLM_MODE` | `live` | `live` \| `stub` \| `offline` |
| `ROUTE_LLM_STUB` | `stubs/responses.json` | файл підготовлених відповідей |
| `ROUTES_DB` | `data/routes.json` | файл сховища |

Файл `.env` **не комітиться** (див. `.gitignore`). У репозиторії лише
`.env.example`.

### Режими AI-компонента

| Режим | Поведінка | Навіщо |
|---|---|---|
| `live` | реальний виклик провайдера | доказ живої інтеграції |
| `stub` | відповідь із `ROUTE_LLM_STUB` за **точним** текстом запиту | детерміновані перевірки сервісу |
| `offline` | імітація недоступності моделі | перевірка збою |

Підміна відбувається **всередині запущеного сервісу**. У публічному API немає
жодного параметра, що перемикає режим, примусово повертає успіх або пише
безпосередньо в сховище.

### Повторний прохід

Кожен повний прохід починайте з **нового тестового сховища**: видаліть
`data/test-routes*.json` перед запуском сервера. `Restart Kernel → Run All`
скидає результати notebook, але **не очищає серверне сховище** — саме тому
сховище треба перезаписувати.

Якщо користуєтеся спільним сховищем, порівнюйте стан до і після за
**ідентифікаторами й полями**, а не лише за кількістю: кількість може не
змінитися, поки запис було перезаписано.

## Звіт

### Вибір задачі

Операція — ведення каталогу туристичних маршрутів вихідного дня. Корисна
операція: маршрути описують люди в розмовних повідомленнях, а каталог
потребує структури. **Базове рішення — правила** (число + одиниця, ключове
слово складності): вони детерміновані, без залежностей і легко перевіряються.
**Межа автоматизації** проходить там, де людина пише не за формою: «легкий
маршружок на 7 кілометрів», «ходимо близько двох годин» — правила тут
потребують винятків, а LLM розуміє формулювання.

### Зв'язок із попередніми темами

- **Навіщо LLM.** Перший notebook показав: правила 8/10, LLM 10/10 на тих самих
  випадках. Різниця — саме на перефразуваннях (C02) і на тексті з вбудованою
  командою (C06).
- **Чому схеми недостатньо.** Тип поля правильний — але число може
  суперечити повідомленню. Перевірка «21 замість 18» ловиться лише
  звіркою з текстом, не схемою.
- **Що зафіксувала специфікація до коду.** Порядок перевірок, межі діапазонів,
  обов'язковість усіх чотирьох полів, відсутність fallback-запису, форму
  тіла помилки.

### Висновок

- **Дослід** установив: правила достатні для канонічного формату, LLM
  потрібна для перефразувань; змістову перевірку числа треба перенести в
  сервіс.
- **Перенесено в сервіс**: чотири перевірки (структура, повнота, діапазон,
  звірка з текстом), нормалізація назви, питання до автора, єдина форма
  помилки.
- **Відомі обмеження**: назва порівнюється за вмістом, а не дослівно (модель
  додає службове слово, а в українській мові назва змінюється за відмінком) —
  строгішого контролю тут немає. Числові поля перевіряються суворо.
- **Запасний маршрут**: ручне створення та список не залежать від моделі;
  при `503` вони продовжують працювати. Fallback-запису немає свідомо (D8).
- **Перевірено самостійно**: чутливість перевірки (окремий тест), незмінність
  сховища за ідентифікаторами, а не лише за кількістю, відсутність доступу
  моделі до сховища (розбір імпортів), відсутність параметрів обходу в API.
